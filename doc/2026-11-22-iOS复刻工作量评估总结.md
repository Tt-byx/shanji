# iOS 复刻工作量评估总结（2026-11-22）

## 用户的问题
评估如果要复刻一个 iOS 端，工作量大不大。（当前项目：闪记，Kotlin + Jetpack Compose 安卓 App + Spring Boot 后端）

## 如何分析的
1. **先量化现有规模**：统计 shanji-android 源码行数——
   - UI 层：15 个文件 / 3480 行（最大：ProfileScreen 540、RecordSheet 507、ChatScreen 502、StatsScreen 329、HomeScreen 230）；
   - 数据层：30 个文件 / 2030 行；
   - 入口/分享页：395 行；**合计约 5905 行 Kotlin**。
2. **识别可复用与必须重写的部分**：
   - 可复用：统计/预算纯函数（Ledger.kt 151 行等，无平台依赖）、云同步与 AI 对话协议、**整个后端（零改动）**、产品设计与 E2E 用例；
   - 必须重做：全部 UI、数据层（Room→SwiftData）、6 个平台特性（小组件/语音/应用锁/截屏分享扩展/分享导出/文件导入导出）。
3. **对比三条技术路线**：SwiftUI 原生重写 / Compose Multiplatform(iOS) / Flutter 重写，按 UI 复用率与平台能力需求评估工作量。
4. **识别硬前提**：Xcode 构建必须 Mac、上架需 Apple 开发者账号、真机测试需 iPhone——用户当前是 Windows 环境，这是第一道门槛。

## 如何解决的
给出三路线对比 + 工作量拆解 + 硬前提清单，并按用途给建议（不给时间估算）：

| 路线 | 工作量 | 要点 |
|---|---|---|
| SwiftUI 原生重写 | 大 | UI 3480 行全重写、数据层重写、平台特性全原生实现；体验与维护最好 |
| Compose Multiplatform(iOS) | 中 | 现有 Kotlin UI/数据层复用 60-70%，需 KMP 化依赖（OkHttp→Ktor）+ 补 iOS 平台实现 |
| Flutter 重写 | 中偏大 | UI 用 Dart 全重写，代码量接近 SwiftUI 方案 |

建议：认真做产品 → SwiftUI；两端功能同步、少写代码 → Compose Multiplatform；先确认 Mac 前提再定路线。

## 最后结果
结论：**工作量大但有明确的省力结构**——后端零改动、统计逻辑可直接移植，主要成本在 3480 行 UI 重写和 6 个平台特性的原生实现；三条路线中 Compose Multiplatform 复用最多（中等）、SwiftUI 体验最好但量最大（大）。**硬前提是必须有 Mac + Apple 开发者账号（上架）+ iPhone（真机）**，用户当前 Windows 环境需先解决此前提。
